# 问道诸天 QQ 机器人：现状架构与玩法审视

**文档版本：** 1.0  
**审视日期：** 2026-07-25  
**适用对象：** 产品策划、主程、CodingAgent、测试与运维

## 1. 结论摘要

当前项目已经具备一个可运行的单人修仙数值游戏闭环：注册/选角、参悟、境界成长、本源、技能、装备、副本、战斗记录、战力排行、药园与炼丹。代码使用 Python 异步函数、FastAPI Webhook 或 botpy WebSocket 两种入口，MySQL 保存玩家与游戏数据。

但是，当前产品的核心体验仍然是“玩家输入指令，系统自动完成一场 1v1 战斗”。它还不是严格意义上由玩家逐回合决策的多人回合制游戏。最大短板不在系统数量，而在战斗会话、多人协作、奖励幂等、QQ 交互可靠性和长期目标没有形成统一架构。

优先级结论：

1. **P0：** 先补安全与基础设施：移除并轮换仓库中的 App Secret、数据库密码和管理员口令；统一入口、身份标识、错误处理、事件去重和事务边界。
2. **P0：** 把现有 1v1 战斗封装成可持久化的 Battle Session，支持回合状态、行动记录、超时、恢复和幂等结算。
3. **P1：** 在 Battle Session 之上实现 2~4 人组队秘境，形成“组队—战斗—奖励—成长”的社交闭环。
4. **P2：** 做新手任务/解锁节奏，解决系统多而主线弱的问题。
5. **P3：** 在多人战斗稳定后再做宗门、地图争夺和赛季。

## 2. 公开玩法调研基线

本节不是照搬其他产品，而是用于判断题材和品类的用户预期。公开资料显示，文字修仙产品常见的长线结构是：挂机修炼、境界突破、装备/功法/丹药/灵兽等多线养成、秘境或副本、宗门/社交、轮回或永久成长。当前公开的多人秘境规划也普遍采用 4 人队伍、手动/自动并存、等待队员提交行动、Boss 机制和职业分工。

参考资料：

- [文字修仙官网](https://fxxkai.com/)，用于观察挂机、境界、秘境和多线养成的公开产品结构。
- [TapTap《文字修仙》官方论坛](https://www.taptap.cn/app/846619/topic)，用于观察 2026 年公开的灵兽、道侣、宗门、冒险和法则等玩法反馈。
- [TapTap 多人回合制秘境规划帖](https://www.taptap.cn/moment/797554493951576994)，用于参考 4 人组队、手动/自动战斗和 Boss 协作方向。该帖是另一产品的规划，不是本项目的需求。
- [QQ 机器人事件订阅与通知](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/interface-framework/event-emit.html)，用于确认 QQ 机器人事件驱动、事件 ID、序列号、Webhook/WebSocket 与重连能力。
- [CN118615717A 游戏组队方法专利](https://patentimages.storage.googleapis.com/ed/9a/af/00699f83a23a3d/CN118615717A.pdf)，仅作聊天机器人组队房间状态的公开资料参考，不直接复制实现。

QQ 官方消息与键盘深层链接在本次审视时发生文档路由变化，具体键盘字段和交互事件必须以 QQ 开放平台当前后台/API 文档为准。产品设计必须保留纯文本指令降级路径，不能把战斗正确性建立在按钮一定可用之上。

## 3. 当前实际架构

### 3.1 运行入口

| 层次 | 当前实现 | 事实来源 | 主要问题 |
|---|---|---|---|
| QQ 接入 | `main.py` FastAPI Webhook；`bot_main.py` botpy WebSocket/SDK | `main.py`、`bot_main.py` | 两套入口存在重复路由、重复限频和不同身份字段，容易出现行为不一致 |
| 消息处理 | `output_content()` → `jiance()` → `content()` | `output_main.py`、`main.py` | 解析与业务分发集中在一个文件，命令规则依赖字符串前缀 |
| 游戏模块 | `Game_main/g0~g9_*.py` | `output_main.py` | 模块按功能拆开，但共享数据库连接和通配符导入，领域边界不清 |
| 战斗引擎 | `Tool/combat_system.py` | `g6_dungeon.py` 调用 | 内存中的 1v1 自动战斗，未提供持久化战斗会话和多人行动提交 |
| 数据层 | `sql/mysql.py` + aiomysql + 多处直接 SQL | 全项目 | 没有统一 Repository/Service 事务边界，多个操作可能跨连接提交 |
| 静态资源 | `images/` 与 `config.py` 中域名 | `main.py`、`config.py` | 部分根路径、文件名和部署文档不一致 |

### 3.2 消息流程

```text
QQ Webhook 或 botpy 事件
    ↓
过滤 / 大写化 / 去除特殊符号
    ↓
jiance()：按无后缀或带后缀命令前缀匹配
    ↓
content()：按命令分发到 Game_main 模块
    ↓
模块打开 MySQL 连接并直接读写
    ↓
返回文本或 Markdown + qqbot-cmd-* 按钮
    ↓
main.py 发送 QQ 回复
```

该流程适合当前单用户指令，但不适合多人战斗，因为它没有 `request_id`、`battle_id`、`round_id`、`action_id`、群上下文和事件去重这些概念。

### 3.3 游戏模块与可见玩法

| 模块 | 当前玩法 | 主要数据 |
|---|---|---|
| 角色 | 注册、选择初始角色、查看角色/属性、出战、角色背包 | `user_zt`、`user_role` |
| 参悟 | 开始参悟、查看状态、领取经验、悟道进阶 | `user_zt` 中参悟字段、`user_role` |
| 本源 | 查看、升级、本源技能 | `data_benyuan`、`user_benyuan` |
| 技能 | 技能背包、激活、技能信息、融合、装备/卸下 | `data_skill`、`user_skill`、`user_role.skill*_id` |
| 装备 | 装备背包、穿戴、卸下、强化、出售、套装属性 | `data_equip`、`user_equip`、`user_role.equip_*` |
| 副本 | 副本列表、怪物列表、挑战副本、挑战怪物、放弃、战斗记录 | `data_dungeon`、`data_monster`、`user_dungeon_progress`、`user_dungeon_drop`、`user_dungeon_daily` |
| 战斗 | 普攻、技能、速度、命中、闪避、暴击、控制、持续伤害、Boss AI | `Tool/combat_system.py`；结果写入战斗日志 |
| 药园/炼丹 | 种植、采摘、丹炉、炼丹、收丹、服丹、加速 | `g9_yaoyuan.py` 使用的药田/丹炉及 `user_item` 等表 |
| 战力 | 综合战力、分项战力、排行 | `user_zt.power*` |
| 交互 | 菜单、Markdown、快捷指令、按钮 | `g0_menu.py`、`Tool/tool_command.py`、`user_command` |

### 3.4 数据模型现状

现有 SQL 已经包含较完整的单人养成数据：角色模板、技能模板、装备模板、怪物模板、玩家角色、玩家技能、玩家装备、背包、本源、副本每日次数和战斗统计。

对多人回合制而言，现有表有三个结构性限制：

1. `user_dungeon_progress` 以 `uid + dungeon_id` 表示唯一进度，一个玩家同一副本只能有一条进行中状态，无法表达多个并发战斗、队伍和战斗快照。
2. `combat_log` 保存的是一场战斗的摘要和文本详情，没有独立的 `battle_id`、`round_id`、`action_id`、随机种子、版本号和结算幂等键。
3. `user_role` 的技能槽是 `skill1_id~skill3_id`，`data_skill` 主要是单技能数值/BUFF字段，当前战斗实体是单个 player 与单个 enemy，目标模型不能表达多个友方/敌方、保护、群体技能和宠物。

## 4. 当前核心玩法闭环审视

### 4.1 已经成立的部分

- 题材识别度强：六个初始角色对应不同世界/本源，副本名称和技能命名有世界观包装。
- 养成反馈完整：等级、境界、属性、装备、技能、本源和战力相互关联。
- 副本内容量足：`data_dungeon` 已有多个世界与大量副本模板，怪物和 Boss 有单独数据。
- 战斗规则不止普攻：已有冷却、法力、命中、闪避、暴击、控制、持续伤害、护盾、反射、吸血和 Boss 分阶段 AI。
- 药园/炼丹提供了等待型资源生产，可作为副本材料和战斗消耗品的长期来源。

### 4.2 体验上的主要不足

#### A. 战斗不是玩家驱动的回合制

`Combat` 内部按速度自动轮流行动，玩家 AI 也由 `_ai_player()` 选择技能。玩家挑战副本时没有提交本回合行动、目标和战术的环节，所以技能数量越多，实际体验仍可能退化为“数值较高的自动战斗”。

**影响：** 技能、控制、治疗和 Boss 机制的策略价值无法充分被玩家感知；多人协作也没有接入点。

#### B. 副本状态是单人进度，不是战斗实例

副本进度记录的是波次、怪物 JSON、击杀数和玩家 HP 比例。它适合单玩家续战，但不适合记录队伍成员、每个单位的精确状态、行动锁、回合截止时间和断线恢复。

**影响：** 不能安全地实现组队、并发战斗和机器人重启恢复。

#### C. 结算与奖励缺少统一幂等模型

项目部分扣物品操作使用原子 `UPDATE ... item_num >= ...`，这是好的局部实践；但战斗、奖励、掉落、次数和战力更新分散在各模块，缺少统一 `reward_txn_id` 和全局结算状态。

**影响：** QQ 重试、用户重复点击、Webhook 重复投递或进程异常时，可能出现重复发奖、扣次失败或状态与消息不一致。

#### D. QQ 交互在群聊中缺少战斗上下文

命令通过字符串前缀匹配，快捷按钮最多保存 5 个槽位，参数命令依赖玩家手动输入。群聊消息没有统一的“当前队伍/当前战斗”上下文，按钮也不能作为唯一可信输入。

**影响：** 多人战斗时容易误操作、串战斗、刷屏；新玩家不知道下一步可做什么。

#### E. 长线目标和系统解锁顺序不清晰

当前系统入口很多，但主线主要由玩家主动探索菜单完成。没有明确的新手任务链、阶段解锁、每日目标、首通目标或组队引导，玩家容易只刷最高可挑战副本。

#### F. 资源和数值缺少可观测性

副本、装备、技能、本源、炼丹都在产出和消耗资源，但没有统一资源流水、来源/去向统计和每日经济报表。战力也由多个分项直接写回玩家表，难以定位数值膨胀来源。

#### G. 工程安全与可靠性风险

- `main.py` 中存在明文 AppID/Secret，`sql/mysql.py` 中存在明文数据库密码，`config.py` 中存在管理员口令；应立即轮换并迁移到环境变量/密钥管理。
- `main.py` 启动时打印 `BOT_SECRET`，属于不必要的敏感信息泄露。
- `main.py` 与 `bot_main.py` 是两套入口，限频字典、返回格式和身份字段不完全一致。
- Webhook 处理使用事件内容，但没有可见的事件 ID 去重表；QQ 重投可能重复执行命令。
- 业务异常被宽泛捕获或部分代码注释掉统一异常返回，玩家可能收到空响应或服务器错误。
- `jiance()` 使用“第一个匹配的前缀”解析，没有正式命令 AST、参数校验和冲突检测。
- `is_txt_exist()` 查询 `./menu/`，而当前仓库根目录没有对应菜单目录，部署后需验证帮助文案是否可用。
- `main.py` 根路径返回的 JSON 文件名与部分部署说明中的 AppID 不一致，属于配置漂移。

## 5. 产品机会与优先级

| 优先级 | 功能 | 解决的问题 | 前置条件 |
|---|---|---|---|
| P0 | 战斗会话持久化、回合行动、超时和恢复 | 让“回合制”从自动计算变成可操作且可靠的系统 | 统一战斗领域模型、事务和幂等 |
| P1 | 2~4 人组队秘境 | 提升 QQ 群互动、职业分工和副本重玩价值 | P0；队伍/战斗实例表 |
| P1 | 新手任务与阶段解锁 | 降低系统复杂度、建立主线 | 命令/奖励/事件流水 |
| P2 | 宗门与赛季地图争夺 | 提供群体长期目标和赛季活跃 | P0/P1；权限与结算服务 |
| P2 | 宠物/灵兽 | 增加队伍编成和资源回收 | 多单位战斗目标模型 |
| P3 | 轮回/永久天赋 | 提供后期重玩与长期保留成长 | 经济与数值报表 |

## 6. 推荐目标架构

```text
QQ Webhook / WebSocket
    ↓
Event Ingest：签名、事件去重、身份标准化
    ↓
Command / Interaction Adapter：命令 AST、按钮 token、降级文本
    ↓
Application Services
    ├── PlayerService
    ├── CultivationService
    ├── BattleService
    ├── TeamService
    ├── DungeonService
    ├── InventoryService
    ├── RewardService
    ├── QuestService
    ├── SectService
    └── AuditService
    ↓
Repository + Transaction Boundary
    ↓
MySQL：状态、事件、流水、审计、定时任务
    ↓
QQ Message Adapter：Markdown、Keyboard、纯文本降级
```

必须遵守：

1. QQ 消息层不能直接修改玩家属性。
2. 所有奖励通过 `RewardService` 发放，并拥有唯一业务键。
3. 所有战斗状态通过 `BattleService` 读取和推进。
4. 所有随机结果写入战斗事件，支持复盘和故障恢复。
5. 群聊只承载公共状态，玩家私有技能/背包信息可以通过 C2C 展示。
6. 按钮数据只携带不可伪造或可服务端重新校验的 token，不能信任客户端传入的伤害、资源或角色属性。

## 7. 推荐开发路线

### 阶段一：基础治理

- 轮换已暴露的 QQ、数据库和管理员凭据。
- 统一使用环境变量；生产日志禁止打印 Secret。
- 保留一个正式入口，另一个入口只作为适配器或开发工具。
- 增加 `event_inbox`、`command_log`、`reward_ledger` 基础表。
- 将命令解析改为明确的命令名、参数、校验错误。

### 阶段二：Battle Session

- 保留现有 `Tool/combat_system.py` 的数值公式作为单人战斗计算内核。
- 新增 Battle/Participant/Round/Action/Effect 领域状态。
- 先支持单人手动战斗，再接自动默认行动。
- 机器人重启后根据数据库状态继续战斗。

### 阶段三：多人秘境

- 先做同群 2 人，再扩展到 4 人。
- 先做固定 Boss 和固定奖励，再做随机事件和复杂掉落。
- 先用文本指令和简单 Markdown，再接按钮交互。

### 阶段四：主线与宗门

- 新手任务覆盖注册、出战、装备、技能、副本、炼丹和首次组队。
- 组队稳定后再做宗门贡献、建筑、领地和赛季。

## 8. 总体验收清单

- [ ] 任何 QQ 事件重复投递不会重复扣资源或发奖励。
- [ ] 任何战斗都能通过 `battle_id` 找到当前状态和完整战斗事件。
- [ ] 机器人重启后未完成战斗可恢复或明确失败补偿。
- [ ] 同一玩家同一回合只能提交一次有效行动。
- [ ] 奖励发放具备唯一键、事务和可查询流水。
- [ ] 群聊与 C2C 的业务结果一致，只有展示方式不同。
- [ ] 所有新增玩法都有资源产出/消耗表、失败路径和管理员审计。
- [ ] 新增模块不再直接依赖 QQ SDK 类型或修改 `user_role` 字段来表达临时战斗状态。
