# 《问道诸天》网页版文字游戏迁移与修仙扩展实施规划

## 1. 目标与边界

本项目将从“以 QQ 消息为唯一交互面”演进为“QQ 机器人与网页双端共用同一套游戏数据和结算规则”的文字修仙游戏。网页版不是另起一套数值服，也不复制已有玩法逻辑；浏览器只增加身份认证、结构化展示和清晰的功能按钮，实际角色、背包、战斗、奖励和 GM 发放仍由现有业务服务与 MySQL 负责。

目标交付包含：

1. 玩家网页：QQ 账号安全绑定、角色总览、今日修行、快捷功能区、文字指令与结果面板。
2. 管理网页：独立入口、独立会话 Cookie、管理员二次校验、玩家与物品查询、单人道具/仙玉发放、完整审计。
3. 双端兼容：同一玩家可在 QQ 和网页查看、操作同一份状态；涉及结算的请求继续使用事务、行锁和幂等业务键。
4. 修仙风 UI：浅色宣纸、水墨山海、朱砂与黛青为主色，按钮文字直接表达动作，不以图标替代关键含义。
5. 修仙扩展：在既有境界、参悟、药园、灵兽、宗门和轮海深渊之上补充洞天游历、道心抉择、天劫和世界事件，但不破坏当前经济闭环。

首期不包含真实充值、第三方 QQ OAuth、玩家自由上传网页素材和跨服。现有 QQ OpenID 不可由浏览器直接提交冒充，网页登录必须由 QQ 内一次性绑定码建立信任。

## 2. 项目现状审计

### 2.1 可直接复用

- `main.py` 已是 FastAPI 入口，可在同一进程挂载网页路由，保留 `/webhook` 不变。
- `bot_main.py` 继续负责 botpy WebSocket；它与网页共用 `output_main.py` 和 `Game_domain/`。
- `output_main.py` 已覆盖注册、角色、参悟、本源、技能、装备、副本、战斗、药园、商城、灵兽、队伍、宗门、世界 Boss、赛季、祈愿、轮回和月卡等命令。
- `Game_domain/gm_service.py` 已有管理员校验、道具/仙玉发放、奖励流水、事务提交和 `request_id` 幂等能力。
- `battle_session`、`event_inbox`、`reward_ledger` 等既有设计可支撑网页重复点击、超时恢复和双端并发。

### 2.2 必须补齐

- 当前 `/` 返回 QQ 平台 JSON，没有玩家网页、浏览器会话或 CSRF 防护。
- 命令结果含 `<qqbot-cmd-input>` 标签，网页需要转换为可读正文和明确按钮。
- QQ 消息层包含平台限频、键盘和图片模式，网页不能直接依赖这些传输层行为。
- 现有 GM 权限保存在 `gm_state.yaml`，网页后台必须额外建立短时管理会话，不能把玩家登录态升级为管理态。
- 没有网页绑定码、网页会话、登录审计和后台访问审计表。

### 2.3 主要风险

| 风险 | 处理原则 |
| --- | --- |
| 浏览器伪造 UID | QQ 内生成一次性短时绑定码；浏览器只提交 UID + 绑定码 |
| 玩家端越权到管理端 | 玩家与管理会话分表字段、分 Cookie 名、分路径校验；后台每次请求复核永久 GM 权限 |
| 双端重复领奖 | 写操作沿用事务、行锁、唯一业务键和 `request_id` |
| QQ 标签污染网页 | 服务端提取命令按钮，网页仅渲染经过转义的有限 Markdown |
| 素材体积过大 | 不复制整包；按页面挑选并记录来源，只提交使用到的压缩资源 |
| 素材授权不清 | 上线前由项目方确认素材包的商用与再分发许可；仓库仅保留已确认资源 |

## 3. 目标架构

```text
QQ Webhook ─┐
            ├─ 命令解析/领域服务 ─ MySQL（唯一游戏状态）
QQ WS ──────┤          │
            │          ├─ battle_session / reward_ledger
玩家网页 ───┘          └─ GM 发放与审计

管理网页 ─ 独立管理会话 ─ GM 权限复核 ─ GM 服务
```

代码分层约定：

- `Game_web/`：FastAPI 路由、网页身份、响应适配和查询服务。
- `web_static/`：HTML、CSS、JavaScript 与经过挑选的网页素材。
- `Game_domain/`：双端共享的结算、奖励和状态规则；任何新玩法不得只写在网页路由里。
- `Game_main/`：继续保留 QQ 指令入口；新玩法需要同步登记命令和网页版动作清单。
- `数据库源文件/`：网页会话、审计与新玩法迁移。

## 4. 身份、会话与隔离设计

### 4.1 玩家登录

1. 玩家在 QQ 发送“网页绑定”。
2. 服务端为当前 UID 生成 10 位、10 分钟有效、一次性绑定码；数据库只存带服务端密钥的 HMAC 摘要。
3. 玩家在 `/play` 输入 UID 与绑定码。
4. 服务端核验后销毁绑定码，签发随机会话令牌；浏览器仅保存 `HttpOnly`、`SameSite=Strict` Cookie。
5. 所有写请求还必须携带会话关联的 CSRF 令牌。

### 4.2 管理登录

1. 永久管理员在 QQ 发送“GM网页绑定”。
2. 只有 `gm_state.is_admin(uid)` 为真时才允许签发管理绑定码。
3. `/admin` 使用不同 Cookie 名和 `/admin` Cookie Path，最长会话 8 小时。
4. 每次后台请求再次复核永久 GM 权限；撤销 GM 后旧网页会话立即失效。
5. 管理 API 不接受玩家 Cookie，不提供从玩家会话“切换管理员”的接口。

### 4.3 审计与敏感信息

- 绑定码、会话令牌、CSRF 原文均不写日志、不写数据库。
- 后台写操作记录操作人、目标玩家、动作、请求 ID、结果与时间。
- 发放继续调用 `gm_service`，保持奖励流水与幂等，不允许网页直接 `UPDATE user_item`。
- 生产环境必须配置至少 32 字符的 `WEB_AUTH_SECRET`，并只通过环境变量注入。

## 5. 网页信息架构与视觉规范

### 5.1 玩家端

- 顶部：玩家名、UID、当前角色/境界、战力、灵石、仙玉。
- 一级入口：今日修行、角色、战斗、洞府、灵兽、宗门、背包、坊市。
- 主内容：服务器返回的文字结果、可执行按钮、参数输入区。
- 快捷动作：参悟/领取经验、签到、日常任务、副本列表、战斗状态。
- 移动端：底部四到五个高频入口；桌面端：左侧导航 + 中央内容 + 右侧状态。

### 5.2 管理端

- 玩家检索：UID、昵称。
- 物品检索：编号、名称、类型。
- 发放表单：目标玩家、物品/仙玉、数量、请求 ID；提交前二次确认。
- 审计记录：操作人、目标、数量、操作结果、时间。
- 管理端不复用游戏页的装饰性动效，以信息密度和误操作防护为优先。

### 5.3 首期素材选择

素材源：`E:\BaiduNetdiskDownload\Q版水墨国风（行侠仗义五千年）`。

- `场景背景/zjm_bg.png`：浅色宣纸水纹，适合作为玩家端可读性背景。
- `UI界面/common_btn_big_yellow.png`：金色按钮底图，可用于主要动作的纹理参考。
- 字体优先复用仓库已有 `MaShanZheng-Regular.ttf` 与 `NotoSansCJKsc-Regular.otf`，避免再复制 17MB 字体包。
- 原素材中的第三方游戏 Logo 不使用；角色立绘只在授权确认和角色语义匹配后接入。

## 7. 分阶段实施顺序

截至 2026-08-21 的实现状态：阶段 A 和阶段 C 已完成代码与单元回归；阶段 B 已交付首版响应式 UI、结构化角色/背包/秘境面板和固定回合战斗按钮；阶段 D 已开始迁移角色、背包、秘境和道心 DTO；阶段 E 的首项“道心问境”已完成双端代码、迁移和单元测试。连接测试库的真实浏览器验收与阶段 E 其余玩法仍待继续。

### 阶段 A：双端基础（P0）

- [ ] 新增网页绑定码、会话和后台审计迁移。
- [ ] 新增“网页绑定”“GM网页绑定”QQ 指令。
- [ ] 挂载 `/play`、`/admin`、玩家 API 与管理 API。
- [ ] 将 QQ 命令标签转换为网页动作按钮。
- [ ] 加入 CSRF、会话撤销、安全 Cookie 和输入长度限制。

验收：同一测试玩家从 QQ 获取绑定码后能登录网页；网页执行“当前角色”后 QQ 再查询结果一致；玩家 Cookie 请求管理 API 返回 401/403。

### 阶段 B：玩家主界面（P0）

- [ ] 完成响应式水墨 UI、仪表信息与高频功能导航。
- [ ] 将参数型命令改造成表单/选择器，避免玩家记忆格式。
- [ ] 战斗状态显示气血、法力、回合、行动按钮和事件记录。
- [ ] 网络错误、重复点击、结算中状态可理解且可恢复。

验收：360px 手机和 1440px 桌面均无横向溢出；所有关键按钮有文字；键盘可操作；连续双击不造成重复奖励。

### 阶段 C：隔离管理端（P0）

- [ ] 玩家/物品检索、单人道具与仙玉发放。
- [ ] 发放确认、结果回显、幂等请求 ID 和审计列表。
- [ ] 管理会话撤销、过期和 GM 权限撤销联动。

验收：非 GM、过期会话、缺少 CSRF、重复请求、超量发放均有覆盖测试；成功发放同时出现奖励流水和 GM 操作记录。

### 阶段 D：网页原生结构化体验（P1）

- [ ] 逐步从“命令适配”迁移到领域服务直接返回 DTO。
- [ ] 角色、背包、装备、药园、灵兽、宗门、坊市拥有结构化 API。
- [ ] QQ 文本渲染器与 Web JSON 渲染器消费同一 DTO。

验收：核心写操作不经 HTML/Markdown 解析；QQ 输出快照测试和 Web JSON 测试同时通过。

### 阶段 E：新增修仙玩法（P1/P2）

1. **道心问境（首版已实现）**：每日一次三选一文字事件，选择影响短期 Buff 与道心倾向；随机结果由 `SHA-256(版本 + UID + 数据库日期)` 的稳定种子生成。
2. **洞天游历**：派遣角色/灵兽探索 2—8 小时，返回资源、奇遇和因果印记；开始时冻结队伍快照。
3. **破境天劫**：特定大境界从“直接升级”变为可准备的天劫会话，丹药、法宝、道心影响容错，不允许无限堆叠收益。
4. **诸天异象**：全服周期事件改变副本词缀、药材产出或世界 Boss 机制，配置版本写入战斗快照。
5. **仙缘札记**：将新手札记扩展为可分支的长期成就线，奖励全部进入 `reward_ledger`。

每个玩法都必须先提供资源产出/消耗表、失败路径、每日/每周上限、幂等键、恢复策略和 GM 审计，再写页面。

#### 道心问境首版规则与保护

| 抉择 | 倾向变化 | 即时产出 | 当日短效 Buff | 消耗 |
| --- | --- | --- | --- | --- |
| 清明 | 清明 +2 | 灵石 60 | 新开始的参悟时长 -10% | 每日机会 1 次 |
| 勇毅 | 勇毅 +2 | 灵石 80 | 新开始的参悟经验 +12% | 每日机会 1 次 |
| 仁心 | 仁心 +2 | 灵石 100 | 新开始的参悟经验 +8% | 每日机会 1 次 |

- 上限：每个 UID 按 MySQL `CURDATE()` 每日只能完成一次；Buff 在次日零点过期，已开始的参悟把效果冻结进 `cw_duration`/`cw_exp`，不受之后状态变化影响。
- 幂等：`dao_heart_daily(uid,event_date)` 唯一；重复 QQ 消息、网页双击或换端重试只回放第一次 `result_json`。奖励流水业务键为 `dao-heart:{uid}:{date}:lingshi`。
- 失败：无效选项在入库前拒绝；玩家不存在、日状态竞争或任意 SQL 失败时整体回滚，不改变灵石、倾向、Buff 和奖励流水。
- 恢复：事件键、版本、种子、选择、请求 ID 和结果 JSON 均落库；刷新网页或发送“道心问境”可恢复当天状态，不重新随机。
- 审计：普通玩家经济变动写入统一 `reward_ledger`，不产生 GM 操作记录；管理员人工补偿仍须使用隔离 GM 发放能力并写 GM 审计。

### 阶段 F：生产发布（P0）

## 9. 完成定义

只有以下证据同时成立，网页版迁移才算完成：

- QQ Webhook、QQ WebSocket、玩家网页和管理网页可同时运行。
- 玩家核心闭环（登录—查看角色—修行—战斗—领奖—养成）无需手输复杂指令即可完成。
- 管理端可以安全查询和发放，且玩家身份不能访问管理能力。
- 所有经济写入有事务与幂等保护，关键后台操作可审计。
- 全量单元测试、数据库迁移演练、浏览器验收与生产回滚演练均通过。
- 素材授权、环境变量、安全密钥和部署文档齐全，不提交真实凭据。
