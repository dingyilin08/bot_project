# 功能建议：多人回合制秘境与组队

**状态：** 建议作为 P1 核心版本实现  
**前置：** 先完成 `02_功能建议_战斗会话持久化与QQ交互.md` 中的 Battle Session 基础  
**目标：** 让 2~4 名玩家在 QQ 群中共同完成一场可操作、可恢复、可结算的回合制秘境

## 1. 范围

### 本期必须实现

- 同一 QQ 群内创建、加入、退出、准备和解散队伍。
- 2~4 名玩家进入固定秘境。
- 每名玩家操控一个出战角色；首期不加入宠物和复杂跑图。
- 每回合提交普通攻击、技能、防御或自动战斗。
- 等待、超时、死亡、掉线和队长退出均有明确处理。
- 固定 Boss 的阶段机制、胜负和奖励结算。
- 奖励幂等、战斗可恢复、战斗事件可追溯。

### 本期禁止扩展

- 不做跨群实时战斗。
- 不做玩家之间交易。
- 不做动态地图编辑器。
- 不把按钮点击作为唯一入口。
- 不在消息处理函数中直接计算伤害或发放物品。
- 不用 `user_dungeon_progress` 继续承载多人战斗状态。

## 2. 用户流程

```text
玩家A：秘境列表
玩家A：创建队伍 赤炎秘境
玩家B/C：加入队伍 <team_code>
队长：队伍信息
所有成员：确认准备
队长：开始秘境
系统：创建 dungeon_instance 与 battle
每回合：成员提交行动
系统：统一排序、执行、结算并发一条战报
Boss死亡：进入奖励结算
系统：写入奖励流水并展示结果
```

队伍代码必须是短期有效的随机值；所有真实身份、队伍归属和副本资格由服务端重新查询。

## 3. 状态机

### 3.1 队伍状态

```text
RECRUITING → READY_CHECK
READY_CHECK → IN_DUNGEON
IN_DUNGEON → IN_BATTLE
IN_BATTLE → IN_DUNGEON
IN_DUNGEON → REWARDING
IN_BATTLE → REWARDING
REWARDING → COMPLETED
```

允许的异常终态：`DISBANDED`、`EXPIRED`、`FAILED`。

规则：

- 只有队长可以选择秘境、开始准备和解散队伍。
- 队伍至少 2 人才能开始；设计上允许 1 人测试，但生产默认 2 人。
- 进入 `READY_CHECK` 后，队伍成员变更必须先取消准备状态。
- 进入 `IN_DUNGEON` 后禁止加入新成员。
- 进入 `IN_BATTLE` 后不允许换角色，不允许修改装备和技能槽。
- 任何状态更新必须使用 `WHERE state = old_state` 的条件更新或版本号，防止并发非法跳转。

### 3.2 战斗状态

```text
CREATED → WAITING_ACTIONS → RESOLVING → ROUND_END
ROUND_END → WAITING_ACTIONS
ROUND_END → WON / LOST / DRAW
```

`RESOLVING` 期间拒绝任何新行动。战斗结束后行动接口只能返回最终战报，不能再次执行。

## 4. 数据库设计

以下 DDL 是建议字段，CodingAgent 必须先对现有 SQL 做字段冲突检查，再生成迁移文件；不得直接修改线上表结构而不备份。

### 4.1 队伍表

```sql
CREATE TABLE dungeon_team (
    id BIGINT NOT NULL AUTO_INCREMENT,
    team_code CHAR(8) NOT NULL,
    group_openid VARCHAR(128) NOT NULL,
    leader_openid VARCHAR(128) NOT NULL,
    dungeon_id INT NOT NULL,
    state VARCHAR(24) NOT NULL DEFAULT 'RECRUITING',
    max_members TINYINT NOT NULL DEFAULT 4,
    version INT NOT NULL DEFAULT 0,
    expire_at DATETIME NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_team_code (team_code),
    KEY idx_group_state (group_openid, state),
    KEY idx_expire (state, expire_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 4.2 队员表

```sql
CREATE TABLE dungeon_team_member (
    id BIGINT NOT NULL AUTO_INCREMENT,
    team_id BIGINT NOT NULL,
    uid INT NOT NULL,
    openid VARCHAR(128) NOT NULL,
    role_id INT NOT NULL,
    ready TINYINT NOT NULL DEFAULT 0,
    member_state VARCHAR(24) NOT NULL DEFAULT 'ACTIVE',
    joined_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    left_at DATETIME NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_team_uid (team_id, uid),
    KEY idx_uid_state (uid, member_state),
    CONSTRAINT fk_team_member_team FOREIGN KEY (team_id) REFERENCES dungeon_team(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 4.3 副本实例表

```sql
CREATE TABLE dungeon_instance (
    id BIGINT NOT NULL AUTO_INCREMENT,
    team_id BIGINT NOT NULL,
    dungeon_id INT NOT NULL,
    state VARCHAR(24) NOT NULL DEFAULT 'IN_DUNGEON',
    node_no INT NOT NULL DEFAULT 1,
    total_nodes INT NOT NULL DEFAULT 1,
    rng_seed CHAR(64) NOT NULL,
    reward_claimed TINYINT NOT NULL DEFAULT 0,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_instance_team (team_id),
    KEY idx_instance_state (state)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 4.4 兼容当前战斗引擎的战斗表

```sql
CREATE TABLE battle_session (
    id BIGINT NOT NULL AUTO_INCREMENT,
    battle_uuid CHAR(36) NOT NULL,
    instance_id BIGINT NULL,
    battle_type VARCHAR(24) NOT NULL,
    state VARCHAR(24) NOT NULL DEFAULT 'CREATED',
    round_no INT NOT NULL DEFAULT 0,
    phase VARCHAR(24) NOT NULL DEFAULT 'WAITING_ACTIONS',
    action_deadline DATETIME NULL,
    rng_seed CHAR(64) NOT NULL,
    engine_version VARCHAR(32) NOT NULL,
    state_json JSON NOT NULL,
    version INT NOT NULL DEFAULT 0,
    result_json JSON NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_battle_uuid (battle_uuid),
    KEY idx_battle_state (state, action_deadline)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

`state_json` 必须是可完整恢复的战斗快照，至少包含单位 HP/MP、BUFF、冷却、行动顺序、技能槽、目标、Boss 阶段和已执行事件编号。

## 5. 指令契约

| 指令 | 参数 | 权限 | 成功效果 |
|---|---|---|---|
| `秘境列表` | 无 | 已注册玩家 | 返回可进入秘境 |
| `创建队伍 <副本名或ID>` | 1 个 | 群内玩家 | 创建队伍并返回 8 位队伍码 |
| `加入队伍 <队伍码>` | 1 个 | 同群玩家 | 加入未开始且未满队伍 |
| `队伍信息` | 无 | 队员/同群可见 | 返回队伍成员和状态 |
| `确认准备` | 无 | 队员 | 设置当前玩家 ready=1 |
| `取消准备` | 无 | 队员 | 设置 ready=0 |
| `开始秘境` | 无 | 队长 | 所有人 ready 且人数达标时创建实例 |
| `离开队伍` | 无 | 队员 | 未开始时离队；开始后进入掉线/托管 |
| `解散队伍` | 无 | 队长 | 结束未开始队伍 |
| `战斗状态` | 无 | 队员 | 返回当前回合和可执行动作 |
| `普通攻击 <目标编号>` | 1 个 | 存活队员 | 提交本回合普通攻击 |
| `释放 <技能ID> <目标编号>` | 2 个 | 存活队员 | 提交技能行动 |
| `防御` | 无 | 存活队员 | 提交防御行动 |
| `自动战斗 开/关` | 1 个 | 队员 | 设置该队员超时默认策略 |

命令解析必须返回结构化错误：`COMMAND_NOT_FOUND`、`INVALID_ARGUMENT`、`NOT_IN_TEAM`、`NOT_LEADER`、`TEAM_FULL`、`TEAM_EXPIRED`、`BATTLE_NOT_FOUND`、`ROUND_CLOSED`、`ACTION_ALREADY_SUBMITTED`、`TARGET_INVALID`。

## 6. 回合结算规则

### 6.1 行动提交

每个存活玩家每回合最多一条有效行动。提交键为：

```text
action_id + battle_id + round_no + uid
```

数据库必须有唯一索引，重复提交直接返回第一次提交结果。

### 6.2 等待与超时

- 普通战斗行动窗口：30 秒。
- 精英/首领战行动窗口：60 秒。
- 所有存活玩家都提交后立即结算，不等待截止时间。
- 超时玩家执行：低于 30% HP 且有可用治疗则治疗，否则普通攻击当前有效目标，无目标则防御。
- 玩家离线、退群或进程重启不阻塞回合。

### 6.3 行动排序

排序键按以下顺序：

1. 行动类型优先级：防御/保护、控制、治疗、攻击；若产品需要速度压制，则改为技能配置中的 `priority`。
2. 单位有效速度降序。
3. 同速度使用本回合稳定随机数。
4. 再以 `actor_id` 升序保证重放一致。

实际优先级必须在配置表中可查，不允许散落在消息处理代码。

### 6.4 结算顺序

```text
读取并锁定 WAITING_ACTIONS 战斗
→ 校验所有行动
→ 补齐超时默认行动
→ 根据稳定排序依次执行
→ 扣除 MP、设置冷却、命中/暴击/伤害/护盾/治疗
→ 处理反射、吸血、持续伤害和持续治疗
→ 更新 BUFF 与冷却
→ 判断单位死亡、胜负和 Boss 阶段
→ 写入 BattleEvent 与快照
→ 发放或预留奖励
→ 提交事务
```

## 7. Boss 与副本首期内容

首期只做 2 个固定副本，验证协作而不是堆内容：

### 赤炎秘境

- 普通怪：炎狼，单体攻击并概率施加灼烧。
- Boss：赤炎蛟。
- 70% HP：获得“火鳞”，火属性伤害提高 30%。
- 40% HP：每 3 回合全体火焰攻击。
- 水属性或净化技能可降低难度。

### 寒霜秘境

- 普通怪：冰魄鸟，概率减速。
- Boss：玄冰蛛后。
- 70% HP：随机冻结一名玩家。
- 40% HP：召唤冰茧；冰茧不击破则下回合全体减速。
- 高速度或驱散技能有明显价值。

Boss 机制必须是可预告的，例如在战报中显示“下一回合将释放全体火焰”，否则玩家无法形成策略。

## 8. 奖励和经济

奖励分为四层：

```text
固定通关奖励
+ 个人参与奖励
+ 机制完成奖励
+ 随机掉落
```

- 贡献不能只按伤害；治疗、承伤、净化、控制和机制处理都要获得参与分。
- 失败不发稀有掉落，但可发少量经验/参与积分，避免失败完全没有反馈。
- 首次通关奖励只能按 `uid + dungeon_id + season_id` 领取一次。
- 所有奖励使用 `reward_ledger.business_key = battle_uuid:uid:reward_type` 唯一约束。
- 战斗次数在副本开始时预扣或在结算时扣除必须二选一；推荐“创建实例时预扣，实例异常终止时按规则返还”，避免重复挑战绕过次数限制。

## 9. QQ 消息策略

群聊只发公共信息，一回合一条汇总战报：

```text
【赤炎秘境｜第 3 回合】
体修A 使用铁壁，获得 25% 减伤
剑修B 对赤炎蛟造成 1280 伤害
丹修C 净化了队友的灼烧
赤炎蛟 HP：42% → 31%
预警：下一回合将释放全体火焰
剩余操作时间：47 秒

可执行：普通攻击 / 释放技能 / 防御 / 战斗状态
```

按钮失败或群聊按钮不可用时，消息必须同时展示可复制的纯文本指令。按钮 token 必须包含 `battle_id`、`round_no`、`action_nonce`，服务端仍需重新校验玩家身份。

## 10. 异常处理

| 场景 | 处理 |
|---|---|
| 队长退出未开始 | 转移队长给加入时间最早的活跃成员；无成员则解散 |
| 队长退出战斗中 | 队伍继续，所有战斗决策不依赖队长 |
| 玩家退群/掉线 | 立即设为托管，按默认策略行动 |
| 机器人重启 | 启动时扫描未结束 `battle_session`，按 `action_deadline` 恢复或推进 |
| 消息发送失败 | 不回滚游戏事务；记录待发送通知，允许重试 |
| 数据库死锁 | 事务重试最多 3 次，仍失败返回“状态处理中”并记录告警 |
| 重复按钮/命令 | 返回原行动或当前回合状态，不重复扣 MP、不重复结算 |
| 战斗快照损坏 | 标记 `CORRUPTED`，停止发奖，生成管理员告警，不自动猜测状态 |

## 12. 测试与验收

### 必须测试

- 2、3、4 人队伍创建与人数限制。
- 非队员不能提交行动。
- 同一玩家同一回合重复命令只生效一次。
- 一名玩家死亡后不能继续提交。
- 超时自动行动；部分队员提交时不提前结算。
- Boss 70%/40% 阶段只触发一次。
- 机器人重启后恢复快照。
- 同一战斗重复请求不重复发奖。
- 两支队伍并发战斗互不影响。
- 群聊和 C2C 指令结果一致。

### 生产验收指标

- 单群 10 支队伍并发，连续运行 1 小时无重复结算。
- 战斗行动提交接口 p95 小于 500ms，不含 QQ API 发送时间。
- 战斗结束后 1 分钟内可查询完整奖励流水。
- 消息发送失败不影响已提交的游戏状态。
