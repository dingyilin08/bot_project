# 功能建议：宗门与赛季地图争夺

**状态：** P2 长线功能  
**前置：** Battle Session、组队秘境、奖励流水、任务/排行榜基础完成后再开发  
**目标：** 将个人成长转化为群体长期目标，增加 QQ 群内的协作、竞争和赛季回流

## 1. 产品定位

宗门不是“多一个菜单”，而是一个把已有角色、装备、技能、副本、药园和战力串起来的组织层。玩家通过贡献参与宗门建设，宗门通过占领有限地图获得阶段性资源优势，赛季结束后重置领地而保留部分荣誉与个人奖励。

核心循环：

```text
加入宗门
→ 完成个人/宗门任务
→ 获得贡献与战功
→ 升级建筑、解锁宝库
→ 组队争夺地图
→ 领取有限期资源加成
→ 赛季结算
→ 荣誉和个人成长保留，领地重置
```

## 2. 本期范围

### 必须实现

- 创建、申请加入、退出和宗门成员管理。
- 宗门等级、贡献值、宗门资金和建筑等级。
- 6 个固定地图节点，每个节点有产出类型和争夺时间。
- 宗门战使用已经完成的多人战斗实例。
- 贡献、战功、参与奖励和赛季奖励流水。
- 赛季开始/进行/结算状态机。
- 管理员和宗门官员操作审计。

### 暂不实现

- 宗门之间实时聊天替代 QQ 群聊天。
- 直接转移玩家装备或灵石。
- 永久占领地图。
- 复杂外交、联盟和跨服匹配。
- 只按宗门总战力一刀切的匹配。

## 3. 宗门规则

### 3.1 基本限制

- 每个玩家同一时间只能属于一个宗门。
- 宗门初始人数上限 20，建筑升级后最高 100；配置化，不写死在命令处理器。
- 宗门创建消耗灵石，创建者自动成为宗主。
- 宗门至少 3 名活跃成员才能参与领地争夺。
- 成员退出宗门后有 24 小时冷却，防止反复转移贡献和奖励。
- 宗门贡献属于玩家历史贡献，不能转账、不能提现、不能直接兑换灵石。

### 3.2 权限

| 角色 | 权限 |
|---|---|
| 宗主 | 解散、任命、副宗主、设置宗门战报名、分配宝库权限 |
| 副宗主 | 审批成员、发起争夺、升级建筑、管理公告 |
| 长老 | 审批成员、发起低级地图争夺、查看战报 |
| 成员 | 捐献、任务、报名、参与战斗、领取个人奖励 |
| 系统 | 开启争夺、结算赛季、发放奖励、清理过期状态 |

所有管理操作写入 `sect_audit_log`，记录操作者、目标、旧值、新值和原因。

## 4. 状态机

### 宗门

```text
ACTIVE → FROZEN → DISBANDED
```

长时间无活跃成员的宗门先进入 `FROZEN`，不直接删除；宗门数据和奖励记录必须可审计。

### 领地

```text
NEUTRAL → CONTROLLED
CONTROLLED → CONTESTED
CONTESTED → CONTROLLED
CONTESTED → NEUTRAL
```

领地争夺只在赛季规定时间窗口发生。控制权有保护期，避免强宗门连续夺取所有节点。

### 赛季

```text
SCHEDULED → SIGNUP → ACTIVE → SETTLING → FINISHED
```

- `SCHEDULED`：生成赛季配置但不能报名。
- `SIGNUP`：宗门报名和选择目标地图。
- `ACTIVE`：允许争夺和占领。
- `SETTLING`：冻结战斗、计算积分和奖励。
- `FINISHED`：发布排行榜，写入个人与宗门奖励。

## 5. 数据库设计

### 5.1 宗门表

```sql
CREATE TABLE sect (
    id BIGINT NOT NULL AUTO_INCREMENT,
    name VARCHAR(32) NOT NULL,
    owner_uid INT NOT NULL,
    state VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
    level INT NOT NULL DEFAULT 1,
    member_limit INT NOT NULL DEFAULT 20,
    funds BIGINT NOT NULL DEFAULT 0,
    contribution_total BIGINT NOT NULL DEFAULT 0,
    notice VARCHAR(255) NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_sect_name (name),
    KEY idx_sect_state (state)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 5.2 成员表

```sql
CREATE TABLE sect_member (
    id BIGINT NOT NULL AUTO_INCREMENT,
    sect_id BIGINT NOT NULL,
    uid INT NOT NULL,
    rank VARCHAR(16) NOT NULL DEFAULT 'MEMBER',
    contribution BIGINT NOT NULL DEFAULT 0,
    season_merit BIGINT NOT NULL DEFAULT 0,
    joined_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    left_at DATETIME NULL,
    state VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
    PRIMARY KEY (id),
    UNIQUE KEY uk_sect_uid (uid, state),
    KEY idx_sect_members (sect_id, state)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 5.3 建筑和地图

```sql
CREATE TABLE sect_building (
    sect_id BIGINT NOT NULL,
    building_type VARCHAR(24) NOT NULL,
    level INT NOT NULL DEFAULT 1,
    PRIMARY KEY (sect_id, building_type)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE season_territory (
    id BIGINT NOT NULL AUTO_INCREMENT,
    season_id BIGINT NOT NULL,
    territory_code VARCHAR(32) NOT NULL,
    name VARCHAR(64) NOT NULL,
    tier INT NOT NULL,
    resource_type VARCHAR(32) NOT NULL,
    control_sect_id BIGINT NULL,
    protected_until DATETIME NULL,
    score_rate DECIMAL(8,3) NOT NULL DEFAULT 1.000,
    version INT NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    UNIQUE KEY uk_season_territory (season_id, territory_code),
    KEY idx_territory_control (season_id, control_sect_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 5.4 贡献与赛季流水

```sql
CREATE TABLE sect_ledger (
    id BIGINT NOT NULL AUTO_INCREMENT,
    business_key VARCHAR(160) NOT NULL,
    sect_id BIGINT NOT NULL,
    uid INT NULL,
    ledger_type VARCHAR(32) NOT NULL,
    amount BIGINT NOT NULL,
    source_id VARCHAR(64) NOT NULL,
    payload_json JSON NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_sect_ledger (business_key),
    KEY idx_sect_ledger_time (sect_id, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE season_reward (
    id BIGINT NOT NULL AUTO_INCREMENT,
    season_id BIGINT NOT NULL,
    uid INT NULL,
    sect_id BIGINT NULL,
    reward_rank INT NULL,
    reward_json JSON NOT NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'PENDING',
    claimed_at DATETIME NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_season_reward (season_id, uid, sect_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 6. 建筑设计

首期只做 4 个建筑：

| 建筑 | 功能 | 升级消耗 | 上限 |
|---|---|---|---|
| 山门 | 提高成员上限 | 宗门资金 | 5 |
| 藏经阁 | 提供技能/参悟任务加成 | 资金+材料 | 5 |
| 丹房 | 提供药园/炼丹效率加成 | 资金+药材 | 5 |
| 战阁 | 提供宗门战报名和战功上限 | 资金+副本材料 | 5 |

建筑加成必须设置上限，且在结算时通过 `SectBonusService` 计算，不能永久写入每个角色的基础属性，否则拆宗/降级难以回滚。

## 7. 领地争夺规则

### 地图层级

| 层级 | 节点数 | 进入条件 | 资源 |
|---|---:|---|---|
| 外围 | 3 | 宗门等级 1 | 灵石、低级材料 |
| 核心 | 2 | 宗门等级 3 | 装备强化材料、技能卷轴 |
| 圣地 | 1 | 宗门等级 5 | 赛季积分、稀有材料 |

### 争夺流程

```text
宗门报名
→ 系统锁定报名名单
→ 匹配 2 个目标宗门
→ 创建宗门战斗实例
→ 参与成员提交战斗行动
→ 统一结算战斗
→ 计算领地分数
→ 更新控制宗门和保护期
→ 写入宗门/个人战功流水
```

匹配不能只看总战力，至少同时考虑：宗门等级、报名人数、近三场积分、最高成员战力和活跃成员数。首期可以用加权分数匹配，但要把输入和结果写入日志，方便调参。

### 反垄断和保护

- 新占领领地保护 24 小时。
- 同一宗门同一周最多发起 5 次争夺。
- 圣地每周只开放一次。
- 连续占领超过 3 个周期后，资源收益衰减至 80%，失守后恢复。
- 低级地图允许新宗门保护报名，避免新宗门永远没有可争夺目标。
- 失败宗门仍获得参与战功，不发领地收益。

## 9. 贡献与奖励

### 贡献来源

- 每日宗门任务。
- 捐献指定副本材料。
- 组队秘境中的机制完成。
- 宗门战参与。
- 赛季目标。

### 贡献消耗

- 建筑升级。
- 宗门任务刷新。
- 争夺报名费。
- 宗门宝库兑换非绑定材料。

### 分配原则

- 宗门收益进入宗门资金或按规则生成个人可领取奖励，不能由宗主手工修改玩家背包。
- 赛季奖励先写 `season_reward`，玩家领取时走统一 `RewardService`。
- 个人奖励同时考虑排名和参与度，避免只奖励宗门第一名的核心玩家。
- 宗门解散时未领取的个人奖励仍保留；宗门资金不直接返还为个人灵石。

## 10. 交互设计

QQ 群消息显示公共信息：领地、报名、战报、宗门公告；个人贡献、可领取奖励和私有库存可以通过 C2C 展示。

推荐一条公共战报：

```text
【第 3 赛季｜赤炎矿脉争夺】
天剑宗  56 分
玄火门  49 分

本轮战况：
天剑宗完成 3 次破盾机制，获得 18 分
玄火门击杀 Boss，获得 20 分
剩余争夺时间：12 分钟

[查看地图] [查看战报] [报名下一场]
```

按钮不可用时必须支持 `宗门地图`、`宗门战报 <ID>` 等文本命令。

## 11. 赛季结算

结算步骤必须是可重试的批处理：

```text
锁定 season = ACTIVE
→ 将赛季改为 SETTLING
→ 冻结领地变更与宗门战报名
→ 计算宗门排名、个人战功和参与档位
→ 写 season_reward
→ 标记本赛季领地 FINISHED
→ 创建下一赛季 SCHEDULED
```

任何一步失败不能重新从头发奖；每个排名奖励使用唯一 `season_id + reward_scope + target_id` 业务键。

## 12. 与现有项目的接入点

- `Game_main/g0_menu.py`：增加宗门入口和赛季入口。
- `output_main.py`：新增宗门命令路由，命令解析不再依赖多个前缀误匹配。
- `Game_main/g6_dungeon.py`：领地战调用 BattleService，不复制战斗公式。
- `Tool/tool_power.py`：只提供战力读取，不把战力直接当作匹配结果。
- `g9_yaoyuan.py`：宗门任务可消耗药材，但必须走 Inventory/Reward Service 的统一流水。
- `sql/mysql.py`：为宗门管理操作提供显式事务。
- `main.py`/`bot_main.py`：只负责接收和发送宗门状态消息。

## 13. 测试与验收

- [ ] 一个玩家不能同时加入两个 ACTIVE 宗门。
- [ ] 宗门人数上限和退出冷却有效。
- [ ] 非宗主/副宗主不能升级建筑或审批成员。
- [ ] 领地保护期内不能发起争夺。
- [ ] 赛季结算期间不能创建新的宗门战。
- [ ] 宗门战奖励、个人参与奖励和赛季奖励均不可重复领取。
- [ ] 宗门资金、贡献和战功都有流水。
- [ ] 断线、重复命令和 QQ 消息重投不会重复捐献、报名或发奖。
- [ ] 赛季结算任务中断后可继续执行，不会重复发奖。
- [ ] 宗门战报能通过 ID 查询，不依赖历史群消息。
- [ ] 低级宗门在保护规则下至少有可参与的地图。
