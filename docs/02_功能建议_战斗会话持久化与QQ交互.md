# 功能建议：战斗会话持久化与 QQ 交互层

**状态：** P0 基础功能  
**目标：** 在不立即改动现有数值公式的前提下，把当前 1v1 自动战斗升级为可查询、可操作、可恢复、可幂等的 Battle Session

## 1. 为什么先做这项功能

当前 `Tool/combat_system.py` 已经有较丰富的 1v1 数值与状态效果，但 `g6_dungeon.py` 直接创建实体、运行战斗并在结束后写结果。战斗中的行动、冷却、BUFF、随机数和中间结果主要存在 Python 对象里；机器人重启、重复 Webhook、消息重试和多人扩展都没有可靠的状态边界。

这项功能的目标不是一次性重写战斗公式，而是增加一个会话层：

```text
命令/按钮
  ↓
BattleService.submit_action()
  ↓
读取锁定的 Battle Session
  ↓
纯战斗引擎 resolve_round()
  ↓
保存快照、事件、结果
  ↓
消息适配器展示
```

## 2. 设计原则

1. **状态在数据库，计算在内存，结果可重放。**
2. **消息不是事实来源。** 消息丢失不代表行动失败，消息重复不代表行动重复。
3. **一次行动一个幂等键。** 同一 `action_id` 只能被接受一次。
4. **一次战斗一个结算键。** 同一 `battle_uuid` 只能结算一次。
5. **所有临时状态显式化。** 不把“正在战斗”藏在 Python 全局变量里。
6. **继续兼容旧副本。** 旧命令可走兼容适配器，新流程走 BattleService。

### 3.2 ActionRequest

```python
ActionRequest(
    action_id: str,
    battle_id: str,
    round_no: int,
    uid: int,
    action_type: str,       # NORMAL_ATTACK / SKILL / DEFEND / AUTO
```

`skill_id`、`target_id`、伤害、消耗和奖励全部由服务端重新查询或计算。客户端提交的值只作为请求意图。


### 4.2 行动表

```sql
CREATE TABLE battle_action (
    id BIGINT NOT NULL AUTO_INCREMENT,
    action_id CHAR(36) NOT NULL,
    battle_id BIGINT NOT NULL,
    round_no INT NOT NULL,
    uid INT NOT NULL,
    action_type VARCHAR(24) NOT NULL,

    UNIQUE KEY uk_action_id (action_id),
    UNIQUE KEY uk_battle_round_uid (battle_id, round_no, uid),
    KEY idx_action_battle (battle_id, round_no)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 4.3 战斗事件表

```sql
CREATE TABLE battle_event (
    id BIGINT NOT NULL AUTO_INCREMENT,
    battle_id BIGINT NOT NULL,
```

### 4.4 奖励流水表

```sql
CREATE TABLE reward_ledger (
    id BIGINT NOT NULL AUTO_INCREMENT,
```

## 5. BattleService 接口契约

```python
async def create_battle(*, uid: int, dungeon_id: int, context: dict) -> BattleView:
    """创建战斗并返回第一回合状态。"""

async def get_battle(*, battle_id: str, uid: int) -> BattleView:
    """只能返回玩家有权查看的战斗。"""

async def submit_action(*, request: ActionRequest) -> ActionResult:
    """提交一次行动；重复请求返回第一次结果。"""

async def resolve_round(*, battle_id: str, expected_version: int | None = None) -> RoundResult:
    """锁定等待中的回合，补齐超时行动并结算。"""

async def recover_stale_battles(*, now: datetime) -> int:
    """启动或定时任务调用，恢复/推进过期回合。"""

async def claim_rewards(*, battle_id: str, uid: int) -> RewardResult:
    """通过 reward_ledger 幂等发放。"""
```

## 6. 事务边界

### 6.1 提交行动

```text
BEGIN
  SELECT battle_session FOR UPDATE
  校验 battle.state = WAITING_ACTIONS
  校验 action.round_no = battle.round_no
  校验 uid 属于战斗且单位存活
  校验技能、目标、冷却、MP
  INSERT battle_action
  若所有存活单位已有行动，标记 ready_to_resolve
COMMIT
```

不能在事务外先扣 MP 再写行动；MP 扣除必须发生在回合结算事务中，避免提交失败造成资源丢失。

### 6.2 结算回合

```text
BEGIN
  SELECT battle_session FOR UPDATE
  检查 state/version
  读取本回合行动
  生成超时默认行动
  调用纯函数 resolve_round(snapshot, actions, rng)
  INSERT battle_event（每个事件）
  UPDATE battle_session.snapshot / round_no / state / version
  若结束：调用 RewardService，写 reward_ledger 与玩家背包
COMMIT
```

随机数必须由 `rng_seed + event_index` 派生，不能直接使用不可追踪的全局 `random` 作为唯一事实来源。若暂时无法重构全部 `combat_system.py`，至少记录每次随机结果和顺序，保证故障后可以复盘。

## 7. 现有战斗引擎改造边界

### 保留

- `CombatEntity` 的属性计算。
- `Skill` 的技能数据读取和效果计算。
- 命中、闪避、暴击、伤害减免、BUFF、持续伤害、治疗、反射和吸血公式。
- Boss/普通怪/玩家 AI 作为超时或自动战斗策略。

### 必须移动或新增

- 将 `Combat.run()` 的“自动循环”拆成 `resolve_one_round()`。
- 为每个行动返回结构化 `BattleEvent`，不能只写字符串日志。
- 不能在引擎里打印控制台作为唯一日志。
- 引擎不能直接访问 MySQL、扣背包或发送 QQ 消息。
- 将 `TargetType` 从 1v1 的 self/enemy 扩展为单体友方、单体敌方、全体友方、全体敌方和随机目标，但可先保留 1v1 兼容实现。

## 8. QQ 交互适配

### 消息标准化

定义统一输入：

```python
IncomingMessage(
    event_id: str,
    source: str,             # webhook / websocket
    channel_type: str,       # group / c2c / guild
    group_openid: str | None,
    user_openid: str,
    content: str,
    interaction_token: str | None,
)
```

`main.py` 和 `bot_main.py` 都必须先转成该结构，再调用同一个 `CommandApplicationService`。当前 `member_openid`、`user_openid`、`union_openid` 的差异必须在适配层统一为内部 `account_key`，不得由游戏模块自行判断。

### 展示降级

优先级：

1. Markdown + Keyboard。
2. Markdown + 可复制命令。
3. 纯文本 + 可复制命令。

每个战斗状态消息都要能通过 `战斗状态 <短ID>` 重建，不能依赖上一条消息仍在聊天窗口中。

## 9. 超时和恢复任务

实现一个可重复执行的定时任务：

```text
每 5 秒扫描 battle_session.state = WAITING_ACTIONS
且 action_deadline < now 的记录
→ 获取分布式/数据库锁
→ 补齐默认行动
→ resolve_round()
```

进程启动时先执行一次恢复扫描；恢复任务失败不得删除战斗。对无法恢复的记录标记 `RECOVERY_REQUIRED` 并报警，由管理员通过命令或后台处理。

## 10. 错误码

| 错误码 | 用户文案方向 | 是否允许重试 |
|---|---|---|
| `BATTLE_NOT_FOUND` | 战斗不存在或已过期 | 否 |
| `NOT_BATTLE_MEMBER` | 你不在这场战斗中 | 否 |
| `ROUND_CLOSED` | 本回合已结算，请查看战斗状态 | 是，查询 |
| `ACTION_ALREADY_SUBMITTED` | 本回合行动已提交 | 是，查询 |
| `SKILL_COOLDOWN` | 技能还在冷却 | 是，换行动 |
| `NOT_ENOUGH_MANA` | 法力不足 | 是，换行动 |
| `TARGET_INVALID` | 目标不存在/已死亡/不可选中 | 是，换目标 |
| `BATTLE_BUSY` | 战斗正在结算 | 是，稍后查询 |
| `REWARD_PENDING` | 战斗已结束，奖励正在入账 | 是，查询奖励 |

## 11. 测试用例

### 单元测试

- 同一快照 + 同一行动 + 同一随机种子得到相同结果。
- 护盾、反射、吸血、持续伤害、控制效果的顺序固定。
- 死亡单位不执行已排队的后续行动，除非技能明确允许复苏。
- 技能扣费和冷却只在有效行动执行时发生。

### 集成测试

- 两个并发请求只插入一条 `battle_action`。
- 两个结算 worker 只允许一个拿到锁。
- 结算事务回滚时不产生奖励流水。
- 结算成功但发送 QQ 失败时，奖励仍存在且消息可重试。
- 重启后从快照恢复下一回合。

### 安全测试

- 修改 `uid`、`battle_id`、`skill_id`、`target_id` 无法越权。
- 伪造按钮 token 无法提交其他玩家行动。
- 重放旧按钮只能得到历史结果，不能重复执行。
